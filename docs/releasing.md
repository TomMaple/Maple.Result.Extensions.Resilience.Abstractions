# Releasing
How a version of `Maple.Result.Extensions.Resilience.Abstractions` is prepared, drafted and published. The other rules
for contributors are in the [conventions](conventions.md).

Pushes to `main` never publish. The CI workflow only builds, tests and uploads a `X.Y.Z-ci.N` package as a workflow artifact.

## Steps
1. **Prepare:** a pull request, merged right before the draft, pins the source links of the reference pages to the tag
   of the release, so that the released commit links to the code it documents:
	* run `python .github/scripts/pin_reference_links.py X.Y.Z` with the version that will be drafted, also for a
	  pre-release (e.g., `3.0.0-rc.2`). Every source link of `docs/Reference` then opens `blob/vX.Y.Z/…`, at the line of
	  the declaration in the working tree. The script refuses a version whose tag exists, and changes nothing while a
	  link to an earlier release opens a declaration that changed (link that member to `main` first);
	* check the result: `python .github/scripts/check_reference_docs.py --release X.Y.Z`;
	* when a release that is not a pre-release was published since the baseline of the package validation, raise
	  `PackageValidationBaselineVersion` to it in the same pull request (see [Package validation](#package-validation));
	* title: `docs: Pinned the source links of the reference pages to vX.Y.Z`.

	Until the release is published, the links name a tag that does not exist yet, so they do not open on GitHub: draft
	and publish soon after the merge.
1. **Draft:** Actions → *Draft release* → *Run workflow* on `main`. It refuses a version whose reference pages do not
   link to its tag (`check_reference_docs.py --release`), calculates the next version, builds and tests, and creates a
   **draft** GitHub Release with notes generated by [git-cliff](https://git-cliff.org/) (`cliff.toml`).
   No tag is created yet; deleting the draft leaves nothing behind.
1. **Review:** edit the notes of the draft in the GitHub UI. When a Dependabot update raised the minimum version of
   `Maple.Result` since the last release, mention it: its `chore(deps)` commit is not in the generated notes.
1. **Publish:** *Publish release* creates the tag `vX.Y.Z` and triggers the *Publish* workflow. Its `build` job packs
   that version with a read-only token; its `publish` job runs in the `nuget` environment (deployments limited to
   `v*` tags), attests the build provenance of the `.nupkg`, pushes it to NuGet (trusted publishing) and attaches the
   `.nupkg`/`.snupkg` to the release.
1. **Verify** the attestation of the package attached to the release (the file on nuget.org carries an extra
   repository signature, so its digest differs). The command hashes a local file, so download the package first;
   without it, it fails with `Loading digest for … failed`:

	```
	gh release download vX.Y.Z --repo TomMaple/Maple.Result.Extensions.Resilience.Abstractions --pattern '*.nupkg'
	gh attestation verify Maple.Result.Extensions.Resilience.Abstractions.X.Y.Z.nupkg --repo TomMaple/Maple.Result.Extensions.Resilience.Abstractions
	```

	It prints the result only in a terminal; in a script, check its exit code (0 when the attestation is valid) or pass
	`--format json`. Once nuget.org has indexed the version, check its page: the README, the icon, the license, the
	symbols, and that its only dependency is `Maple.Result`.

If *Publish* fails, fix the cause and use **Re-run failed jobs**: it reuses the package of the first build, and the
`publish` job skips whatever is already on NuGet or attached to the release. *Re-run all jobs* builds a new package,
so it fails once the version is on NuGet, rather than attach a package that differs from the published one.

Never create, move or delete a `v*` tag by hand: the `release-tags` ruleset protects them, and *Publish release*
creates them.

Release notes list only `feat`, `fix`, `perf` and breaking commits. `docs:`, `chore:` (including dependency bumps),
`test:`, `ci:`, `build:`, `style:` and `refactor:` commits never appear, and neither do PR merge commits unless they
are marked breaking. Preview the notes locally with `git cliff --unreleased --strip all`.

## Version
* Calculated from the commits since the last `v*` tag: `!` or a `BREAKING CHANGE:` footer bumps major, `feat` bumps
  minor, anything else bumps patch.
* To override it, enter a version (e.g. `3.0.0`) in the *version* input when running *Draft release*.
* Pre-release: enter e.g. `3.0.0-rc.2`. The draft is marked as a pre-release automatically. The notes of the final
  `3.0.0` then list only the commits after the last release candidate; merge the notes of the release candidates when
  editing it.
* The versions follow those of the core and its other companion packages: the releases of 3.0 are 3.0.0 pre-releases,
  and the package references the version of `Maple.Result` that it needs, which is its minimum version.

## Package validation
* `dotnet pack` validates the package (`EnablePackageValidation` in
  `src/Maple.Result.Extensions.Resilience.Abstractions/Maple.Result.Extensions.Resilience.Abstractions.csproj`) and
  compares its public API with the package of the baseline version (`PackageValidationBaselineVersion`): a removed
  member or a changed signature fails the pack, in CI and in *Publish*. It catches a breaking change that was committed
  without `!`, which would otherwise be released as a minor or a patch version.
* The baseline is the latest published release that is not a pre-release. The *Prepare* pull request raises it after
  every such release (e.g., to `3.1.0` when preparing `3.1.1` or `3.2.0-rc.1`), so that each release keeps the API of
  the one before it, not only that of the first release of its major version. A pre-release is never the baseline, as
  the API of a release candidate may still change before the release.
* The baseline package is restored from nuget.org, so a version that is not published yet cannot be the baseline: the
  restore fails with `NU1102`. Until 3.0.0 is published, the project has no baseline and only the package itself is
  validated; the *Prepare* pull request of the first release after 3.0.0 sets it to `3.0.0`. To compare with a
  pre-release by hand (e.g., in a pull request that should add members only), pack with
  `-p:PackageValidationBaselineVersion=3.0.0-rc.1 -p:Version=3.0.0-rc.2`.
* An intended breaking change of the next major version: generate the suppressions with
  `dotnet pack src/Maple.Result.Extensions.Resilience.Abstractions/Maple.Result.Extensions.Resilience.Abstractions.csproj -c Release -p:Version=X.0.0 -p:GenerateCompatibilitySuppressionFile=true`
  and commit `src/Maple.Result.Extensions.Resilience.Abstractions/CompatibilitySuppressions.xml` with the change, so that
  each break is listed and reviewed in its pull request. Pass the version of the next major release: without it, the
  assembly version is `1.0.0.0`, lower than the baseline, and the file gets a false `CP0003` entry (CI always passes the
  version). The *Prepare* pull request that raises the baseline to the new major version deletes the file.
